# Escalation Execution — Hard-Won Lessons

Extracted verbatim from `SKILL.md`'s "Escalation execution: hard-won lessons"
section on 2026-10-03 (sha256[:12] = `1414d28af5e6`, 6155 chars).

**When to read:** during escalation EXECUTION — after an issue has been classified
and before a Tier 1/2 fix or a `user_gated` filing. Not needed for the scan itself
(that's `execution-loops.md`); these are the lessons about repairing, gating,
validating, and diffing.

Themes: repair the CLASS not the member · negative controls before trusting green ·
`user_gated` is a claim to be tested · diff backup FILES and assert the net
substitution · force-verification can race the store you are writing to · a
corrected measurement can invalidate the row that cited the old one.

---

**Repair the CLASS when the unit of the finding is a key/member/job, not the member itself.** An issue that has recurred N times by being repaired one member at a time has the wrong repair unit, and the Nth fix is not the last. Measured 2026-10-02: `oc_env_scope_profile_keys_unread_20260926T051500Z` recurred three times (2026-09-29 mirrored 2 keys and explicitly deferred "26 further profile-only keys remain unmirrored -- they are latent"; 2026-10-02 03:32Z mirrored `DISPATCH_QUOTA_*`; 2026-10-02 22:07Z mirrored `SEARXNG_URL` after live web_search damage). Each pass repaired exactly one key and left the class open, so the deferral *was* the recurrence mechanism. The closing pass mirrored all 8 remaining non-secret keys in one append and added a parity probe. **Rule:** when the same issue_id has been repaired member-by-member more than twice, stop, enumerate the whole class, and check whether the correction WEAKENS anything — here it did not, and that must be stated. Corollary: a "latent, not currently damaging" verdict is a promise to re-derive the same list next time; if the list will be re-derived anyway, enumerate it now.

**A negative control is the only thing that distinguishes a passing detector from a broken one — and it catches the fixer, not just the fixee.** The env-parity probe above reported `PARITY OK` on its first live run. A synthetic world with the same drift shape then proved the probe actually flagged drift — and in doing so caught that my exclusion list was a hardcoded `{"WIKIPEDIA_USERNAME"}`, which is the same defect class as this skill's own hand-picked-regex lesson (it would never cover a second key). Two further defects surfaced only because the control kept running: a suffix-stripping rule missed `WIKIPEDIA_PASSWORD_HEX`, and a service-prefix rule then failed to pair `SOME_USERNAME` with `SOME_API_TOKEN` until identity pairing was matched on the **shared first-segment prefix** instead. Three published-green states, each invalidated. **Rule:** every new detector ships with a synthetic-world negative control run BEFORE its clean result is trusted, and when a rule must enumerate exceptions, derive the exception by a RULE rather than a literal name list — the literal list is the bug waiting for the second key.

**A `user_gated` flag is a CLAIM about the fix path, not a verdict on the risk — test the path before honoring it.** A scan escalates as `user_gated` by reasoning about the *obvious* remedy, and that reasoning usually names a specific mechanism. If it does, read the CLI's actual surface before accepting the gate: a sanctioned per-entity edit usually exists and makes the feared blast radius unreachable. Measured 2026-10-02: `oc_custodian_cron_prompt_carries_discarded_5x_headroom_formula_20261002T2015Z` was filed `user_gated` with the reason "editing two prompts inside the 392KB cron/jobs.json registry; a malformed write deschedules all 158 jobs." `hermes cron edit <id> --prompt` edits ONE job atomically and never rewrites the file. The gate was falsified, the fix applied in two commands, revalidated, and the issue closed. **Rule:** run `hermes cron edit --help` before concluding a cron job's prompt/schedule/name is uneditable, and escalate such an edit as user-gated only after checking that surface. Same family as the `custodian.scan.light` lesson above — confirm the surface before concluding anything.

**Diff the backup FILE, never a reconstructed snapshot — and assert the NET substitution, never the shortest span.** Two of my own assertions were wrong while the edit was right, and both surfaced only because the comparison ran against a real file:
- **Reconstructed snapshot + wrong key = mass phantom drift.** I captured a pre-change meta dict, then later read `schedule.expr` as `schedule`, so 143 jobs reported `schedule: '0 * * * *' -> None`. The registry had not changed. Re-reading the backup file and diffing full JSON objects removed every phantom. The real state of the volatile fields was corroborated by a *separate* proof: a 12s idle re-read with no action taken moved `fire_claim`/`next_run_at`/`last_dispatch`/`pending_slot` on 2 jobs by themselves, proving them scheduler-owned. **Classify scheduler-written volatile fields separately; never let their drift fail a config-integrity assertion.**
- **Shortest-span matching absorbs the common tail.** In a prefix/suffix diff, ` - used` is common to both strings and lands in the suffix, so the reported "changed span" is `4 * avail` -> `0.80 * (used + avail)` rather than the whole expression, and an equality assert on the span fails. The net substitution was correct all along. **Rule:** gate on `apply(SUBSTITUTION, original) == live`; report the shortest span as evidence only.
- **`$(cat file)` strips trailing newlines** before the value reaches `--prompt`, costing 1 byte at end of string. Expect it and reproduce it in isolation rather than discovering it as an unexplained length mismatch.

**Force-verification can contend with the store you are writing to.** `hermes cron run <id>` is the usual post-fix close-the-loop step, but when the target job appends rows to the same `issues.jsonl` this run just wrote, forcing it creates a concurrent-append race for no gain. When the assertion under test is a *text* signature in the registry, re-reading the registry after the edit IS the re-validation. Record the behavioral confirmation as **pending, with the specific check and the scheduled run that will produce it** (2026-10-02: the 20:00Z `custodian:light` run must publish `deficit_to_80` in the ~3.4 GB class, not 17-18 GB) rather than declaring it verified or silently skipping it.

**A corrected measurement can invalidate the row that cited the bad one.** When a fix corrects the *method* an earlier row used, check whether that row's own figure survives. Here the 19:23Z light scan published `deficit_to_80 = 18.06 GB` from the discarded formula; the corrected answer is ~3.4 GB. Row 336 already carried the corrected 3.53 GB figure and was unaffected — but under last-row-wins that has to be checked, not assumed, because a superseded figure can still be the last word on an issue.
