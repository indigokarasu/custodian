# Execution Loop -- Deep Scan

Runs on optimized 6-hour cron schedule. Isolated session, lightContext.

1. **Load context** -- own journals (7 days), `fix_effectiveness.jsonl`. Identify recurring fingerprints, known-failed fixes, already-searched queries. **Build confidence summary**: for each active fingerprint, note `confidence_score` and `recommended_tier`.
2. **Collect** -- full day gateway log, cron run logs, skill journals from scan window, all OCAS data dirs, the platform diagnostic tool.
3. **Fingerprint + classify** -- match against `references/known_issues.json` then `learned_issues.jsonl`. **Apply confidence override**: if fingerprint has `confidence_score >= 0.6` and `recommended_tier == 1`, classify as Tier 1 even if source says higher tier. Unknowns default Tier 3.
3b. **Root cause analysis** -- for each classified fingerprint with `recurrence_count >= 2`, check `rca.jsonl` for an existing root cause record:
   - **No RCA record exists** (first recurrence): execute the drilldown procedure from `references/root-cause-analysis.md`. Create an RCA record in `rca.jsonl` classifying the pattern (A-E), identifying the variable, and forming a root cause hypothesis. If Pattern B (fix applied but didn't hold), do NOT re-apply the previous fix — escalate to Tier 3 with the RCA evidence attached.
   - **RCA record exists, Pattern A** (fix never applied): proceed with the fix as normal.
   - **RCA record exists, Pattern B** (fix didn't hold): do NOT re-apply the same fix. If a root-cause-level fix was designed in a previous RCA, attempt that instead. If no root-cause fix has been designed yet, escalate with the full RCA record.
   - **RCA record exists, Pattern C** (different root cause): decompose into sub-fingerprints, create new RCA records for each distinct cause.
   - **RCA record exists, Pattern D** (transient): mark as `transient_dormant`, skip fix, do not escalate.
   - **RCA record exists, Pattern E** (cascade): apply the fix to the upstream trigger, not the downstream symptom. Record the co-occurrence correlation in the RCA.
   - **Fix-loop detected** (same fix applied >= 3 times, `schedule_adjusted_stickiness < 0.5`): auto-escalate to Tier 3 with the full occurrence chain. Do not apply the fix again regardless of confidence score.
4. **Rebuild activity model** -- parse gateway log `message.processed` events (`source: user` vs `source: cron`). Blend Corvus if present (70/30). Update `activity_model.json`. Determine `current_state`.
5. **Optimize schedule** -- score current schedule against activity model. If score < 6, compute better schedule. Shift max 30 min per slot. Update cron if changed.
6. **Skill conformance** -- scan installed skills, parse `## Background tasks`, cross-reference against the platform scheduling registry (jobs.json). Register missing cron tasks (Tier 1). Surface mismatches (Tier 2). **Also run the cron registry health sub-pass** (Step 6b, see below).
6b. **Cron registry health** -- parse `{agent_root}/cron/jobs.json` (see control char cleaning pitfall below). Three checks, all Tier 1:
   - **Dead skill references**: for each job with a `skills` array, verify every listed skill directory exists under `{agent_root}/skills/`. Remove non-existent skill entries from the array, or delete the job if the skill was its only purpose.
   - **Dead script references**: for each job with a `script` field, verify the script file exists on disk. Update or delete the job if missing.
   - **Duplicate function detection**: group jobs by `script` path, by prompt prefix (first 200 chars), and by display `name`. If multiple jobs share the same script/prompt/name, keep the one whose name matches the SKILL.md canonical name (or the earliest ID), and delete the rest. Log all deletions in the action journal.

**⚠️ Orphaned job detection:** A cron job is orphaned when its `name` doesn't match any declared background task in any OCAS skill's SKILL.md `## Background tasks` section AND it has `last_status: null` AND `last_run_at: null`. Orphaned jobs consume cron slots and add registry noise. Remove them (Tier 1). Always verify against actual SKILL.md declarations before removing — some jobs may have slightly different names than their SKILL.md declarations (e.g., `Vesper: Morning Briefing` in cron vs `vesper:morning` in SKILL.md). Use fuzzy matching on skill tag + schedule pattern. See `references/orphaned-job-detection.md`.

**⚠️ Pitfall — Never remove a job whose script exists and is declared in SKILL.md:** A job with `last_status: null` and `last_run_at: null` is NOT necessarily orphaned. It may be a newly declared task that has never run yet (e.g., declared in SKILL.md but the cron registration was missed during init). Before removing, always: (1) Check if the job name appears in any SKILL.md `## Background tasks` section, (2) Check if the referenced script file exists on disk. If both are true, the job is declared but unrun — NOT orphaned. Register it (Tier 1 fix) instead of removing it. Example: `haiku:haiku-post` was incorrectly removed on 2026-05-13 as "orphan" despite being declared in ocas-haiku SKILL.md with a valid script at `skills/ocas-haiku/scripts/haiku-post.js`. It had to be re-registered on 2026-05-14.

**⚠️ Pitfall — New job with future `next_run_at` is NOT orphaned (2026-05-16):** A job with `last_status: null`, `last_run_at: null`, but `next_run_at` set to a future timestamp is a newly created job waiting for its first scheduled run. It is NOT orphaned. Example: `weave:sync-google` was created on 2026-05-15 with `next_run_at=2026-05-17 04:00` — it had never run simply because its first scheduled window hadn't arrived yet. Only flag as orphaned if `next_run_at` is also null or in the past. Always check `next_run_at` before concluding a job is orphaned.

**⚠️ Pitfall — Skills declare cron jobs in TWO places (2026-05-16):** Skills can declare background tasks in either or both of:
1. `## Background tasks` markdown table (parsed by looking for `| Job name | Mechanism | Schedule | Command |` rows)
2. YAML frontmatter `metadata.hermes.cron` array (parsed by finding `cron:\n` in the frontmatter and extracting `name:` fields)

Many skills (ocas-haiku, ocas-taste, ocas-weave, ocas-spot) declare cron jobs ONLY in the frontmatter, not in a Background tasks table. If you only check the Background tasks table, these jobs will falsely appear "undeclared." Always parse BOTH locations. The frontmatter cron section looks like:
```yaml
metadata:
  hermes:
    cron:
      - name: "job:name"
        schedule: "0 0 * * *"
        command: "skill.command"
```

**⚠️ Pitfall — Frontmatter contains non-job name: fields (2026-05-17):** The frontmatter `cron:` array is NOT the only place `name:` fields appear. Skills also declare API key names (e.g., `ALPHAVANTAGE_API_KEY`, `clay_api_key`, `google_contacts_oauth`) and MCP server names (e.g., `marriott`, `flights`, `mempalace`). A naive regex extracting ALL `name:` fields will pick these up as "missing cron jobs." Always filter:
- Names matching `_[A-Z_]+_(KEY|SECRET|TOKEN|API|ID|URL)$` (uppercase API keys)
- Names matching `_(api_key|oauth|secret|token)$` case-insensitively (lowercase API keys)
- Names that are MCP server descriptors (have `description:` but no `schedule:` field)

See `references/frontmatter-cron-parsing.md` for the full parsing code pattern.

**⚠️ Pitfall — Conformance parsing must extract only job-name-style identifiers (2026-06-06):** When parsing SKILL.md Background tasks tables and frontmatter cron arrays for conformance checking, extract ONLY colon-separated job-name-style identifiers (e.g., `bower:scan`, `custodian:deep`). Do NOT extract schedule strings (e.g., `0 0 * * *`), description text (e.g., "Self-update from GitHub source"), or command text (e.g., "python3 ~/.hermes/scripts/email_check.py"). A naive regex that extracts all backtick-wrapped content or all table cells will produce false positives — schedule strings and descriptions will appear as "missing cron jobs." Use the pattern: `` `([a-z][a-z0-9_-]*:[a-z][a-z0-9_-]*)` `` for backtick-wrapped names, and filter frontmatter `name:` fields to only include values containing a colon (to exclude API key names and MCP server descriptors).

**⚠️ Pitfall — All tasks use cron, not heartbeat:** Hermes has no heartbeat mechanism. All background tasks are registered via `cronjob(action='create', ...)`. The `mechanism: heartbeat` value in SKILL.md Background tasks tables is legacy from OpenClaw — ignore it. All tasks go in jobs.json.

**⚠️ Pitfall — Never register a job that isn't explicitly declared in SKILL.md:** The skill conformance check (Step 6) should only register jobs that are explicitly listed in a SKILL.md `## Background tasks` table or frontmatter `cron:` array. Do NOT invent job names or register jobs based on assumptions about what "should" exist. If a job name doesn't appear in any SKILL.md, it is not a declared background task — it is either orphaned (remove) or a user-created job (leave alone). Example: `scout:sources-refresh` was incorrectly registered by a deep scan on 2026-05-14 because the scan assumed it should exist, but the `ocas-scout` SKILL.md only declares `scout:update` and `scout:research`. It had to be removed as an orphan on the very next scan cycle.
7. **Skill init pass** -- initialize any skill missing data dir, config.json, or journal dir.
8. **Repair pass** -- all Tier 1 fixes (including confidence-promoted ones). Activity-aware: if active, only urgent fixes (failure in last 5 min); defer rest. Register verify jobs. Execute prior deferred fixes if now quiet.
9. **Web search pass** -- for unknown fingerprints with `recurrence_count >= 1`, run next mutation query (see Web Search Protocol).
10. **Escalation pass** -- Tier 3/4 open issues that the confidence model did NOT reclassify: include `briefing` payload in journal. Tag journal `escalation_needed: true`. **Before escalating, check confidence model**: if fingerprint now has `confidence_score >= 0.6` from a recent successful fix, auto-fix instead.
11. **Report** -- `{agent_root}/commons/data/ocas-custodian/reports/YYYY-MM-DD-HHMM.md`. Include confidence model summary: fingerprints tracked, promotions/demotions this cycle. If all clean and previous cycle also clean: suppress Vesper signal.
12. **Write journal** -- Action (if fixes applied) or Observation (scan-only).
13. **Update confidence model** -- for each fix applied this cycle, update `fix_effectiveness.jsonl` with outcome. Recompute `confidence_score` and `recommended_tier` for affected fingerprints. **Update schedule_adjusted_stickiness** for each resolved fingerprint: compute `cycles_survived / (1 + recurrence_count)`. If `schedule_adjusted_stickiness < 0.5` and `recurrence_count >= 2`, trigger Pattern B drilldown (Step 3b) on the next scan.
14. **Update RCA records** -- for each RCA record touched this cycle, update `rca.jsonl` with the outcome: whether the root-cause fix was applied, whether the fingerprint has recurred since, and updated `schedule_adjusted_stickiness`. Close RCA records where `schedule_adjusted_stickiness > 2.0` for 7+ consecutive days (fix held across 2+ schedule cycles per recurrence for a full week). Escalate open RCA records that have been active for >7 days without resolution.

**Evidence retention:** Each deep scan should write a session evidence file to `references/deep-scan-YYYY-MM-DD.md` capturing: confirmed pitfalls exercised, fix counts, script path issues, MCP failures, memory trends, and any new patterns discovered. These files are concise and for the value of the task, not full transcripts.
**⚠️ Pitfall — Orphan detection false positives from over-broad matching (2026-06-03):** When cross-referencing declared tasks against cron jobs.json, use EXACT name matching — not prefix/suffix/partial matching. A naive "skill prefix match" (e.g., `corvus:deep` matching any job starting with `corvus:`) will flag 58 of 105 jobs as "orphaned" because most cron jobs share skill prefixes with declared tasks but have different function suffixes. The correct approach: (1) Build a set of exact declared names from both `## Background tasks` tables (strip backticks) and frontmatter `cron:` arrays (strip quotes, filter API keys/MCP names). (2) Compare each cron job's `name` field against this exact set. (3) Only flag as orphaned if `last_status IS NULL AND last_run_at IS NULL AND next_run_at IS NULL or in the past`. Jobs with `last_status: ok` or `error` are NOT orphaned — they are active jobs that may have been created by the user or by skills that don't declare background tasks in SKILL.md (e.g., `Gateway health monitor`, `thread-renamer:*`, `dream-journal:*`, `rainbow-grocery-receipts`). These are user-created or infrastructure jobs that custodian should leave alone.

**⚠️ Pitfall — `oc_config_empty_section` Pattern B (2026-06-18):** The config.yaml empty sections fix has been applied 2x (2026-06-17 and 2026-06-18) — sections reappear after gateway restart. If applied a 3rd time, do NOT re-apply. Escalate to Tier 3 with root cause "gateway config migration regenerates null keys from template." Fix direction: investigate what writes these keys back (gateway startup, config migration, or template), and add a post-startup hook or config validation step that strips null sections automatically.

**⚠️ Pitfall — `last_status=error` with `consecutive_failures=0` means transient:** When scanning error jobs, always check `consecutive_failures`. If it's `0` (or `null`), the error is a single-occurrence transient failure from the most recent run — NOT a persistent issue. Do NOT escalate or apply fixes. Only jobs with `consecutive_failures >= 1` have genuinely failed multiple times. This pattern commonly appears with mass HTTP 429 rate limits where many jobs fail simultaneously but the scheduler doesn't count them as consecutive failures. The `state.db` `sessions` table has columns `started_at` and `ended_at` — NOT `created_at`. Querying `WHERE created_at > datetime('now', '-14 days')` will crash with `sqlite3.OperationalError: no such column: created_at`. Always use `started_at` for time-based session filters. The full column list is: `id, source, user_id, model, model_config, system_prompt, parent_session_id, started_at, ended_at, end_reason, message_count, tool_call_count, input_tokens, output_tokens, cache_read_tokens, cache_write_tokens, reasoning_tokens, billing_provider, billing_base_url, billing_mode, estimated_cost_usd, actual_cost_usd, cost_status, cost_source, pricing_version, title, title_source, archived, api_call_count, handoff_state, handoff_platform, handoff_error, cwd, rewind_count`.

**⚠️ Pitfall — Skill directory path may not match skill ref name (2026-06-06):** A cron job's `skills` array may reference a skill name (e.g., `ocas-elephas`) that doesn't directly match a top-level directory under `skills/`. The skill may exist at a nested path (e.g., `skills/elephas/ocas-elephas/`). Before flagging a skill reference as dead, search recursively: `find {skills_dir} -name "SKILL.md" -path "*/{skill_name}/*"`. If the job's `last_status` is `ok`, the skill is clearly being found by the runtime — the directory layout is non-standard but functional. Do NOT flag as `oc_cron_dead_skill_ref` in this case.
