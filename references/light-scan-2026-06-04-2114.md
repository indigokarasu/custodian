# Light Scan 2026-06-04 21:14 UTC

## Findings Summary

### Mass Cron Scheduling Gap After Gateway Downtime

**Scenario**: 92 of 105 cron jobs showed overdue `next_run_at` values. Initial assessment was "post-downtime fast-forward pattern" — but deeper analysis revealed a genuine scheduling gap.

**Key Diagnostic Discriminator**:
- Fast-forward pattern (benign): `next_run_at` stale BUT `last_run_at` recent (within schedule interval), `last_status=ok`
- Genuine scheduling gap (actionable): `next_run_at` stale AND `last_run_at` >48h old for **most** jobs simultaneously

When >85% of jobs are simultaneously stale, this is a **mass event**, not individual job failures. Root cause is gateway downtime — the scheduler's in-memory state was lost on restart and `jobs.json` on-disk values were not updated.

**Verified Data**:
- Gateway downtime: ~67 hours (2026-06-01T19:19 → 2026-06-04T10:34)
- 90 of 92 overdue jobs had `last_run_at` >48h old
- 84 of 92 had `last_status=ok` before the gap (not failing — just not being triggered)
- All 5 HTTP 429 errors were from before the downtime (stale, not active)
- `jobs.json` `updated_at` was current (2026-06-04T18:00) but `next_run_at` values were all stale

**Verdict**: `oc_cron_stuck_missed` mass event. Tier 2 (beyond auto-repair scope for 92 jobs). Escalation needed: manual scheduler reset required (`hermes cron resume --all` or equivalent).

## Lessons

1. **Mass overdue diagnostics**: When scanning for stale `next_run_at`, always count how many jobs are simultaneously stale. If >85%, this is a gateway downtime / scheduler state divergence event, not individual job failures. Don't triage each job individually — escalate the root cause.

2. **Stale error absorption**: After a gateway downtime event, ALL pre-existing error jobs likely have stale errors. The `consecutive_failures=None` + old `last_run_at` combination is the signal. Don't create new issues for these — they'll self-resolve when the scheduler resumes.

3. **jobs.json updated_at is misleading**: The file's `updated_at` timestamp reflects the last scheduler write, but `next_run_at` values in the file are not updated by the scheduler after `--replace` restart. The timestamps can be fresh while the schedule data is stale.
