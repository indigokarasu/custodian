# `fallback_model: null` YAML Debris Pattern

## Summary

When a `fallback_model` entry is removed from `config.yaml` (e.g., a broken manifest.build or ovhcloud provider), a **null key remnant** can persist in the file as `fallback_model: null`. This is NOT a true fix-loop where the gateway regenerates the key on restart — it is **YAML debris** from an incomplete prior removal.

## Distinction: True Fix-Loop vs YAML Debris

| True Fix-Loop | YAML Debris |
|---|---|
| Key reappears after gateway restart | Key persists unchanged across restarts |
| Gateway config migration/template re-inserts | The value was never fully removed from disk |
| Requires hook or startup fix | Requires one-time cleanup |

## Root Cause

The Hermes `save_config()` function in `hermes_cli/config.py` writes the full config dict via `yaml.dump()`. If the config dict contains `"fallback_model": None`, YAML serializes it as `fallback_model: null`. This can happen when:

1. A provider is removed from `fallback_model` but the key itself remains as `None`
2. A partial edit (e.g., `sed`) removes the indented sub-keys but leaves the `fallback_model:` line
3. A Python script deletes the value (`config['fallback_model'] = None`) without deleting the key (`del config['fallback_model']`)

## Diagnosis

```bash
# Check for null fallback_model
grep "^fallback_model:" <hermes-home>/profiles/indigo/config.yaml

# Check all null root-level keys
python3 -c "
import yaml
with open('<hermes-home>/profiles/indigo/config.yaml') as f:
    data = yaml.safe_load(f)
nulls = [k for k, v in data.items() if v is None]
print('Null keys:', nulls)
"
```

## Fix

Use PyYAML to properly remove the key (not set it to None):

```python
import yaml

with open('<hermes-home>/profiles/indigo/config.yaml', 'r') as f:
    data = yaml.safe_load(f)

if 'fallback_model' in data and data['fallback_model'] is None:
    del data['fallback_model']  # Remove the key entirely

with open('<hermes-home>/profiles/indigo/config.yaml', 'w') as f:
    yaml.dump(data, f, default_flow_style=False, sort_keys=False)
```

**Do NOT use `sed '/fallback_model/d'`** — this can match indented `fallback_model:` inside provider definitions and delete the wrong line.

## Escalation Runner Context

When the escalation runner finds `fallback_model: null` in config.yaml:
1. **Do NOT classify as a fix-loop** unless you can prove the key is being regenerated after deletion + gateway restart
2. **Default assumption:** it's YAML debris. Remove it once and close the issue.
3. **Only escalate as fix-loop** if the key reappears after: (a) confirmed removal from disk, (b) gateway restart, (c) no manual re-addition
