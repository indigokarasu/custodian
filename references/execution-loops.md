# Execution Loops

## Light Scan (every heartbeat)

Run the following checklist in order. Do not skip steps — each gates the next.

- [ ] 1. Read `jobs.json` (the profile cron registry at `$HERMES_HOME/../<profile>/cron/jobs.json`; NOT via `hermes cron list`, which reads the wrong path). **Parse robustly**: the registry is a top-level object whose job list lives under the key `"jobs"` (a list) — use `d.get("jobs", [])`. A few older/copied registry copies *do* wrap the list under `data.jobs`; only fall back to `d.get("data", {}).get("jobs", [])` if the top-level `"jobs"` key is **absent**. **CRITICAL FALSE-CLEAN GUARD**: if your parse yields `len(jobs) == 0`, re-inspect the raw file head (`head -c 600 jobs.json`) before concluding anything — a wrong key silently returns 0 jobs and risks a false `[SILENT]` on a misparse. Confirmed 2026-07-16: a parse using `data.get("jobs")` returned 0 jobs on a live registry that actually holds 148 (top-level `"jobs"`); the false-clean risk was caught only by re-inspecting the raw file.
- **⚠️ TWO REGISTRIES EXIST — STATE WHICH PATH YOU PARSED (confirmed 2026-09-27):** `/root/.hermes/cron/jobs.json` (root) and `/root/.hermes/profiles/<profile>/cron/jobs.json` (profile) are DIFFERENT live files with DIFFERENT job counts — 155 vs 157 on the same host in the same minute, neither a symlink to the other. For this profile the **profile** path is authoritative. A journal that silently reads the root file reports a coherent but WRONG registry: a job enabled only in the profile tree is invisible, and vice versa. **Rule:** every journal's `registry.source` names the absolute path AND the parsed job count; when a prior journal's count differs from yours, do not assume either is right — state both and declare which is authoritative for the profile. Same class as the log-set-pinning pitfall: the artifact is the input set, not the system.
- **Post-fix registry verification**: after resetting merge-conflict skill repos and re-running `update_skill.sh`, the `jobs.json` registry still shows stale `last_status=error` until the next scheduled execution. Force-flip with `hermes cron run <job_id>` and verify `last_status` flipped to `ok`.
- [ ] 2. Tail gateway log for new errors since last scan timestamp
    - **⚠️ LOG TIMESTAMPS ARE LOCAL, NOT UTC (confirmed 2026-09-26):** the journal `timestamp` field is UTC (`...Z`), but the lines inside `errors.log` / `agent.log` / `gateway.log` are stamped in **local time** (PDT, `-07:00`). A scan that copies the UTC journal timestamp into a string comparison against log lines gets a silent mismatch and reports **zero errors** — a false clean. Confirmed 2026-09-26: baseline `2026-09-26T13:16:51Z` was compared against local `06:xx` lines; every line sorted as "before cutoff" so the scan printed `(none)` and `(no ERROR lines since cutoff)`, which read as a clean bill of health. CONVERT the baseline before use (13:16:51Z = 06:16:51 PDT), and after any scan that reports zero new errors, confirm the cutoff actually brackets recent log lines (`tail -1 <log>` vs `date`) before accepting the clean verdict. Same class of bug as `references/jobs-json-timestamp-offset-misread-pitfall.md` on the registry side.
    - **⚠️ TRACEBACK CONTINUATION LINES BREAK STRING COMPARISON (confirmed 2026-09-26):** a Python traceback body line (`openai.APITimeoutError: Request timed out.`, `httpx.ConnectError: [Errno 111] Connection refused`) carries **no timestamp**. Lexically, `openai....` sorts AFTER `2026-09-26 11:32:39`, so a naive `line.replace("T"," ")[-19] > CUTOFF` filter counts every un-stamped continuation line in the file as "new" — regardless of which hour it was actually written. A 2026-09-26 light scan's first pass reported **18 phantom `conn_refused` hits and 3 phantom `APITimeout` hits**; the second pass with carry-forward attribution returned **0** for both, confirming they were stale Sep-25 traceback bodies. **Rule:** parse `^(20\d\d-\d\d-\d\d)[ T](\d\d:\d\d:\d\d)` off each line; when a line has no timestamp, inherit the previous line's timestamp. Re-run any scan that surfaces a *provider/network* class and confirm the first hit's timestamp is genuinely inside the window before believing the count. **Refinement (2026-09-27):** once carry-forward is applied, do not count the `Traceback (most recent call last):` header or its `File "..."` frames as separate events at all — collapse a traceback to its **terminal exception class** and count that once per (job, timestamp). A 105-min window with 46 traceback headers and ~160 frames is really 2 events, not ~200; counting frames is how a small window manufactures a large number. Same class as the UTC-vs-local cutoff pitfall directly above.
    - **⚠️ `errors.log` MIRRORS `agent.log` WARNING LINES — A 4-FILE WARNING COUNT IS EXACTLY 2x (confirmed 2026-09-27):** this is the *mirror* sibling of the log-set pinning rule below, and it is the form that actually bites. Measured over 2026-09-27 03:09–04:21: the `never claimed (scheduler stopped before dispatch)` WARNING appears **130x in `profiles/indigo/logs/agent.log` and 130x in `profiles/indigo/logs/errors.log`**, with 130/130 unique-signature overlap and `errors - agent = 0`; both ROOT copies carry 0. So `errors.log` is not a rotation artifact of `agent.log` — it is a **subset copy for WARNING-class lines**. Any scan that unions WARNING lines across the 4-file set reports double. A 2026-09-27T11:25Z journal published `unclaimed_occurrences_in_window=260` where the truth is 130 (~108/hr, not 260/hr). **Rule:** count WARNING-class lines from `agent.log` ONLY and state in the journal that `errors.log` mirrors them; reserve the `errors.log` sweep for ERROR/CRITICAL lines, which are NOT duplicated. Same signature as the log-set pinning pitfall — the tell is a count that is *exactly* 2x when you add `errors.log`. Re-inflating an already-corrected series with a mirror artifact is a regression, not a finding.
    - **⚠️ PIN THE LOG-FILE SET FOR ANY RATE/TREND CLAIM (confirmed 2026-09-26):** rotated logs make counts non-comparable across runs. `/root/.hermes/logs/agent.log` and `agent.log.1` plus their `/root/.hermes/profiles/indigo/logs/` twins all carry `already running — skipping` lines. Counting one file gives 573/day, four files give 1818/day. Three consecutive journals escalated `oc_cron_scheduler_duplicate_subscription` on a "354 → 514 → 1815 GROWING" series that was entirely a file-set artifact — a single pinned 4-file set over full hours reads 155/176/151/151/157 (mean 158/hr, spread 25, flat). **Rule:** every trend claim uses one fixed file set, enumerated in the journal, compared on full-hour buckets, and never a cumulative day total against a bounded window. If the per-hour spread is within ~25 of the mean, the verdict is `flat`, not `growing`. This is the log-side twin of the verifier false-LIVE / false-DORMANT bugs below.
    - **CRITICAL GATEWAY-TRACEBACK GAP (2026-07-22):** A jobs.json-only scan can report "clean" (0 actionable error jobs) while the gateway is throwing **recurring plugin-code tracebacks** that NEVER surface as a `jobs.json` `last_error`. These come from gateway-internal paths (e.g. `conversation_compression.py`, `chronicle/engine/store.py`), not from cron job scripts. Example signatures found 2026-07-22: `sqlite3.IntegrityError: CHECK constraint failed: actor IN (...)` in `chronicle/engine/store.py:append_event`, and `TypeError: ChronicleContextEngine.compress() got an unexpected keyword argument 'force'`. Both recurred 14–19× pre-restart, 0× post-restart. Detection procedure:
      - `grep -nE "Traceback|IntegrityError|TypeError|ERROR gateway" <gateway.log>` since the last gateway restart line (`Received SIGTERM` / `Starting Hermes Gateway`).
      - **WHICH `gateway.log` IS LIVE (2026-07-24):** there are TWO. `~/.hermes/logs/gateway.log` (root) is a **stale copy** (last entries June 2026 in this deployment) — grepping it returns pre-restart noise and MISSES live July tracebacks. The **live** log is `$HERMES_HOME/../<profile>/logs/gateway.log` (the one `verify_plugin_defect_postrestart.py` reads); plugin tracebacks also land in `~/.hermes/logs/errors.log`. Verify recency (`grep -oE "20[0-9]{2}-[0-9]{2}-[0-9]{2}" <file> | tail -3`) before trusting any `gateway.log`, and run the post-restart verifier against the LIVE path. Full recipe + confirmed case: `references/gateway-log-live-vs-stale-path-2026-07-24.md`.
        - **⚠️ BOTH CAN BE LIVE — "one is stale" is not a durable fact (re-checked 2026-09-26):** the note above was true on 2026-07-24 and is **not** a stable invariant. On 2026-09-26 `lsof` showed the single `hermes` process (pid 3115331) holding BOTH `~/.hermes/logs/gateway.log` and `~/.hermes/profiles/indigo/logs/gateway.log` open for writing, with the profile copy quiet since 10:55 and the root copy live at 11:58 — the exact inverse of the guidance. The profile copy is quieter only because gateway event volume is bursty, not because it stopped. **Rule:** never infer which log is live from a prior scan's conclusion or from mtime alone. `lsof <file>` (or `fuser -v`) is the ground truth for "is anything still writing this"; scan BOTH files every time. A quiet-but-open log is a false-clean risk only if you mistake it for a dead one.
      - Dedup signatures (exception class + in-plugin frame, e.g. `store.py:append_event` / `compress() got ... 'force'`), collect first/last timestamps.
      - Drop signatures already represented by an OPEN issue in `issues.jsonl` (grep fingerprint/issue_id) — don't double-track.
      - Drop single-shot / pre-restart-only signatures that have NOT recurred post-restart (noise).
      - For a NEW recurring signature with NO open issue: persist as `status: open`, `escalation_needed: true`, `user_gated: false`, `recommended_tier: 4` (plugin code defect — NOT credentials, NOT user-gated). Append race-safely (`cat >> issues.jsonl << 'PYEOF'`, one JSON object per line) — never a whole-file rewrite the top-of-hour `custodian:light` pass could clobber. Record `new_issues` in the journal.
    - See `references/gateway-log-traceback-gap-detection.md` for the reusable recipe + known-signature catalog. **VERIFIER FALSE-LIVE BUG (fixed 2026-07-24):** `verify_plugin_defect_postrestart.py` previously bucketed each signature hit against the *nearest preceding* restart, so logs with many restarts always reported `post_restart_total>0 → LIVE` (false positive) and would re-escalate resolved issues. It now uses the MOST RECENT restart only. Before acting on any LIVE verdict, independently confirm with `awk 'NR>=<last_restart_lineno>' <log> | grep -cE "..."` — if 0 but verifier says LIVE, the verdict is wrong. Detection recipe + regression note: `references/verify-plugin-defect-postrestart-false-live-bug.md`. **VERIFIER FALSE-DORMANT (inverse, confirmed 2026-07-25):** the verifier only counts signatures in its curated regex catalog; an uncatalogued or regex-mismatched signature reports `post=0 → DORMANT` even when actively recurring post-restart. Confirmed: `compress_force` recurred at `2026-07-24T16:51:12Z` (after the 15:25:08Z restart) but the verifier said `post=0`; independent `awk` proved 1 post-restart hit, so a `resolved` issue was wrongly left closed and had to be REOPENED. The raw-grep window in Step 2 is the AUTHORITATIVE live signal; the verifier is advisory only. Rule: if verifier says DORMANT but the raw-grep window contains the signature post-restart → treat as LIVE, reopen/escalate; do NOT trust DORMANT. Full recipe: `references/verify-plugin-defect-postrestart-false-dormant-2026-07-25.md`.
- **⚠️ ROOT AND PROFILE `gateway.log` CARRY THE SAME EVENTS (confirmed 2026-09-29):** unlike `errors.log` (a WARNING subset copy) and `agent.log` (a root/profile split), the two `gateway.log` files can hold the **same lines verbatim**. Measured 2026-09-29 12:00:31-36: a 6-file union reported 32 in-window events where the truth is **16**, because each of the 4 abort events appeared in both gateway copies. **Rule:** collapse gateway events by `(timestamp, message)` before fingerprinting and say in the journal that the dedup was applied. A count that is *exactly* 2x on a gateway sweep is this artifact, not a doubled failure rate. Same tell as the mirror rule, opposite mechanism — there the duplicate is a subset, here it is a full copy.
- **⚠️ VERIFY THE TWO REGISTRIES ARE SEPARATE FILES — THE HARDLINK STATE IS NOT AN INVARIANT (re-checked 2026-09-29):** the "⚠️ TWO REGISTRIES EXIST" warning above (155 vs 157, "neither a symlink to the other", confirmed 2026-09-27) does **not** hold on this host today. `ls -i` shows `/root/.hermes/cron/jobs.json` and `/root/.hermes/profiles/indigo/cron/jobs.json` are the **same inode (25279)** — hardlinked, so the two paths cannot disagree. The hazard is real in general but is a per-scan check: run `ls -i` and record `same_inode: true/false` in `registry`. Corollary: with a hardlink there is no independent "root copy" to diff against for a write-isolation check, and a file-level write to one path rewrites the other. Also note `state.db` shows the same pattern (both paths reported 0.83 GiB on 2026-09-29).
- [ ] **UNICODE HOMOGLYPH IN LOGGED FILENAMES (confirmed 2026-09-30):** an ERROR that reads `media file not found` / `No such file` on a path that LOOKS correct is a prime suspect for U+202F NARROW NO-BREAK SPACE, U+00A0, or a curly quote inside the name. macOS/AppleScript screenshot names (`Screenshot 2026-09-30 at 1.00.29 AM.png`) use U+202F before AM/PM and the attachment writer preserved it; the reader rebuilds the name with an ASCII space, so the file EXISTS and the lookup still fails — and the error message prints the ASCII form, so the log actively conceals the cause. Measured 2026-09-30: 8 occurrences of that one name across the log set, each a "missing" file that was on disk. **Rule:** when a missing-file error names a file you believe exists, run `ls <dir> | cat -A` (or compare `repr()` of the on-disk name to the logged name) BEFORE classifying it as a real failure — a missing file that is present is never a missing file. Tier 1 mitigation is an **additive ASCII-space hardlink alias** (`os.link`), never a rename: renaming breaks the original path for every other holder. Revalidate by importing and calling the real failing function on both names, and run the **inverted test** (move the alias aside, confirm the original error returns, restore, confirm the pass returns). A bare pass proves nothing when the control path passes trivially — the first two of my three probes were themselves buggy (wrong signature, then an AttributeError in the print after prep had already succeeded) and reporting either as a pass would have been a false completion. Durable fix is filename normalisation in the attachment writer, which is framework code and outside the non-destructive envelope.
- [ ] 3. Fingerprint each new error (match against known patterns in `references/`)
- [ ] **A `free_only ... not a :free SKU` WARNING is about the RESOLVED model, not the top-level one (confirmed 2026-09-30):** `_aux_openrouter_settings()` reads top-level `auxiliary.openrouter_model`, but `_try_openrouter(model=...)` gates on `or_model = model or cfg_model`, where `model` is the CALL-SUPPLIED vision model. So a valid `auxiliary.openrouter_model: nvidia/...:free` does NOT prevent the warning when `auxiliary.vision.model` holds a composite like `openrouter/free` (provider/model, not a real SKU) — `_is_free_model` rejects it. Two traps: (a) checking only the top-level config makes this look like a false positive on the already-resolved `oc_auxiliary_paid_lane_free_only_disabled` issue, and (b) on a profile deployment the value may come from the **ROOT** `config.yaml` while the profile file holds the correct settings — `get_config_path()` resolves root when `HERMES_PROFILE` is unset in the calling context. **Rule:** reproduce with a live call (`_try_openrouter(model=<value from auxiliary.vision.model>)`) and read `cfg_get(cfg,'auxiliary','vision','model')`, rather than reasoning from config greps. Confirm scope split by checking whether the logs show the provider you pinned. Impact is usually one wasted round-trip, not an outage — do not escalate as a vision failure. Root-file edits are NOT a safe Tier 1 fix here (another profile may legitimately consume that copy).
    - **⚠️ STRIP THE TIMESTAMP+MS PREFIX BEFORE MATCHING NUMERIC STATUS CODES (confirmed 2026-09-29, measured):** every Hermes log line is stamped `YYYY-MM-DD HH:MM:SS,mmm LEVEL ...`, so the **millisecond field itself contains the bare tokens `503` / `402` / `429`** with no marker. A matcher that greps the RAW line for a provider status code cannot distinguish "HTTP 503" from "this INFO line happened at .503 seconds". **Measured on this host: a naive substring match for these three codes hits 8,742 lines across 147 rotated log files, and 1,806 of those (20.7%) match ONLY because of the millisecond field** — logging prefixes were `hermes_cli.web_server`, `hermes_cli.plugins`, `gateway.run`, `photon_platform.adapter`, `cron.jobs`, i.e. nothing provider-related. Sampling every affected line found just **1** carrying a real status reference. A light scan on 2026-09-27 reported 10× `oc_provider_503_upstream_capacity`, 2× `oc_provider_402_credits` and 5× `oc_provider_429_rate_limited` inside a 47-minute window; stripping the prefix reduced all three to **ZERO**. This is the same structural class as the mirror-dedup and traceback-collapse rules and, like them, **scales with log volume — the busiest hours are the ones most likely to fabricate an outage escalation**, including a `user_gated` 402-credits row that would burn operator attention on a non-existent outage. **Rule:** before any numeric status match, strip the leading `^\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2},\d{3}\s` prefix (and any bracketed `[,NNN]` ms field some loggers emit) and match against the remainder. Non-numeric patterns (`never claimed`, `database is locked`, `context window of 2048`) are unaffected. **Symptom check:** if a provider fingerprint appears on lines that are all `INFO`/`WARNING` with no status word, suspect this before anything else. `references/log-signature-msfield-false-positive.md`.
- [ ] 4. Check failed fixes from previous scan — verify each fix held
- [ ] 5. Check uninitialized skills (missing storage, no background tasks registered)
    - This includes checking for missing data directories, journals directories, and config files. **Canonical paths are `{agent_root}/commons/data/{skill}/` and `{agent_root}/commons/journals/{skill}/`** (see `references/conformance.md` § Skill Initialization and `references/fix-missing-skill-data-directories-2026-06-30.md`). **⚠️ Pitfall — wrong-path guess:** do NOT check `skills/<skill>/commons/data/` or `skills/<skill>/commons/journals/` — those subdirs do not exist; every active skill would falsely report missing dirs and waste a check cycle. Confirmed 2026-07-14: a light scan guessed `skills/<skill>/commons/data` and flagged 32 false-missing dirs before correcting to `commons/data/<skill>` (all present).
    - See references/fix-missing-skill-data-directories-2026-06-30.md and references/fix-missing-skill-journals-directories-2026-06-30.md for fix procedures
    - **⚠️ SECOND WRONG-PATH VARIANT — the IN-PACKAGE check (confirmed 2026-09-26):** the 2026-07-14 pitfall above is about checking `skills/<skill>/commons/...`. A subtler variant is checking `skills/<skill>/data/` and `skills/<skill>/journals/` — i.e. looking for the dirs INSIDE the skill package. No skill has them; the dirs live in the profile's `commons/` tree. A 2026-09-26 light scan did exactly this and reported **13 of 24 cron-referenced skills as uninitialized** (ocas-custodian, mentor, praxis, rally, reach, sands, scout, styx, taste, vesper, forge, weave, util-skill-analytics) when all 13 were correctly initialized. Before writing ANY uninitialized-skill finding, confirm the path is `<profile>/commons/data/<skill>/` and `<profile>/commons/journals/<skill>/`. If a probe returns a suspiciously HIGH uninitialized count (a majority of referenced skills), suspect the probe, not the system — that ratio is the tell.
        - **⚠️ THIRD WRONG-PATH VARIANT — toolsets, not skills (confirmed 2026-09-26):** a job's `skills[]` array can hold BARE TOOLSET names, not skill names. `skill-analytics-daily` carries `skill: util-skill-analytics` + `skills: ["terminal", "file"]` — `terminal` and `file` are toolsets that have no skill package and no commons dirs. A probe that unions every string in `skills[]` into the active-skill set reports `data/terminal`, `journals/file`, etc. as 4 missing dirs, i.e. an uninitialized-skill count fabricated entirely by the probe. **Rule:** when unioning the active-skill set, treat a `skills[]` entry as a skill ONLY if `/root/.hermes/skills/<name>/` exists as a directory; otherwise it is a toolset and is excluded. Re-derive the missing count after the exclusion — if it was the majority of your findings, the probe was wrong (same tell as the two variants above). Signature of this class: a "missing" name that is a single common noun (`file`, `terminal`, `browser`, `web`) rather than a hyphenated skill name.
- **CRITICAL: cross-reference against active cron jobs before flagging.** A skill with missing data/journals dirs but NO cron jobs referencing it (via `skill:` or `skills:[]`) is uninitialized-but-unused — note it in the journal as info-only, do NOT escalate. Only flag for remediation if at least one active cron job depends on the skill. Confirmed 2026-07-01: 10xeng-autofix and skilllab had missing dirs but zero cron job references — not actionable.
- **⚠️ FOURTH WRONG-PATH VARIANT — state-only skills have no journals dir by design (confirmed 2026-09-26):** the three variants above are all about probing the WRONG path. This one is the inverse: the path is right, the *expectation* is wrong. A skill whose package **declares no journal output path at all** has nothing to write there, so a missing `commons/journals/<skill>/` is not a gap. Confirmed 2026-09-26: the corrected-path probe reported 7 skills as `data=True journals=False`; cross-checking each against the journal path its own package declares split them into **3 genuine gaps** (ocas-haiku, ocas-vibes, ocas-weave — each declares a `commons/journals/...` output path) and **4 probe artifacts** (ocas-autobio, ocas-styx, ocas-usercontext, restaurant-rater — declare zero journal paths, are state-only, write only to `commons/data/`). Creating dirs for the 4 artifacts would have been 4 phantom fixes, and re-flagging them every scan is a recurring false positive. **Rule:** a `journals=False` finding is actionable ONLY if the skill's package declares a journal output path. Verify with `grep -rhoE "commons/journals/[A-Za-z0-9_./{}$-]*" <skill_dir> | sort -u`; 0 hits = state-only skill, record info-only and exclude from the uninitialized count. Same tell as the other three variants: a high uninitialized count is more likely a wrong expectation than a broken system.
  - **Also match the NAME, not just the dir:** a skill may journal under a variant name (`commons/journals/weave/` while the skill is `ocas-weave`). An existing non-empty variant dir is a naming inconsistency to record for a future consolidation decision — NOT a missing dir, and NOT a light-scan removal target.
    - **Re-derive the active-skill set from the LIVE jobs.json every scan** — union the `skills` (array) AND `skill` (scalar) fields across ALL job entries; treat any skill appearing ≥1 time as actively referenced. Confirmed 2026-07-07: a prior scan reported `browser-vision`, `generative-art-algorithms`, `generative-art-deployment`, `ocas-lucid` as "unused (no cron refs)" — but all four ARE referenced (by `art:studio` and the `lucid:*` jobs). The cross-ref had silently dropped them, so they were wrongly left un-remediated while `art:studio` ran with missing data/journals dirs. If a skill dir is missing AND the live set contains it, remediate — **but first check WHICH dir is missing** (see `references/dead-skill-ref-active-job-fix.md`): if the skill dir itself is absent because the skill was **archived/merged** (not merely uninitialized), do NOT recreate it — remove the dead `skill`/`skills[]` reference from the job (`skill: null`) instead. Recreating a fake skill directory is the wrong fix for an archived skill. Only `mkdir + config.json` when the skill dir exists but its `data/`/`journals/` subdirs are missing. **never trust a prior scan's 'unused' label**; always re-derive from the live file.
- [ ] 6. Check error jobs for script path blocks and `Path.home()` resolution issues
    - **DE-AGGREGATE identical wrapper messages.** When ≥2 error jobs share a bare `Script exited with code 1` (or any identical low-information) `last_error`, they are NOT one root cause. Enumerate each, read its `script` field, and determine the REAL per-job failure (run the script; inspect `sys.exit` paths; for subprocess wrappers, run the wrapped command). A no-op-by-design exit (no stderr) is `oc_cron_no_agent_exit_1_noop` (Tier 2 surface-only); a traceback is a real failure. Confirmed 2026-07-07: a prior scan collapsed three distinct jobs (`monitor:list` 403, `monitor:journals` no-op, `SearXNG` infra) into one bucket and omitted `monitor:journals`. See `references/no-agent-script-exit-1-deaggregation-pitfall.md`. Use `scripts/classify_error_jobs.py` to surface every ambiguous wrapper job with its `script` name.
    - **MASKED-EXIT-1 VARIANT (no output at all):** A no_agent wrapper may call the real worker as a subprocess and convert ANY non-zero to `sys.exit(1)` with NO stdout/stderr forwarded (see `monitor_list.py` → `tasks_monitor.py`). In that case `last_error` is the bare `Script exited with code 1` AND a live re-run of the wrapper shows empty output — the real traceback is HIDDEN. To de-aggregate, run the WRAPPED script directly (`python3 <skill>/scripts/<worker.py> --mode check`) and read ITS traceback. If the live signature differs from any resolved covering issue → it is a NEW failure with no open issue (Step 8b/8e gap); persist it. Confirmed 2026-07-14: `monitor:list` failed live with `KeyError: 'access_token'` — masked by the wrapper, referenced only by two already-resolved issues → gap closed by writing `oc_google_tasks_access_token_missing`. See `references/monitor-list-exit1-mask-gap.md` and `references/monitor-list-masked-keyerror-pitfall.md`.
- [ ] 7. Check for jobs not running (stale `last_run_at` vs expected schedule)
- **CRITICAL**: `next_run_at < now` alone is NOT sufficient. Must verify: `last_run_at` older than 2× schedule interval AND `last_status != ok`. High-frequency jobs (≤10 min) show scheduler state lag where `next_run_at` hasn't advanced but job ran successfully. See `references/scheduler-state-lag-vs-execution-failure.md`.
- **Never-run job (`last_status=None` AND `last_run_at=None`):** NOT a stuck-scheduler failure if `next_run_at` is still in the future — the job has simply never been due. Only flag as "not running" when `next_run_at` is ALSO past. Convert `next_run_at` to UTC before comparing (it carries an offset, e.g. `-07:00`; see `references/jobs-json-timestamp-offset-misread-pitfall.md`). ## Escalation Runner Checklist

- [ ] 1. Check latest esc-run journal first (5-sec check vs 60-sec full scan)
- [ ] 1b. **Already-classified fast path**: If the prior esc-run journal is < 2h old AND classified all open issues as `open_user_gated` AND no new `last_error` messages in `jobs.json` AND no new entries in any `issues.jsonl` → write journal referencing the prior classification and return `[SILENT]`. See `references/escalation-runner-already-classified-fast-path.md`.
- [ ] 2. Discover ALL `issues.jsonl` paths: `find <hermes-home> -name "issues.jsonl"`
- [ ] 3. Deduplicate by `issue_id`/`id` — keep best status per entry
- [ ] 4. For each open issue, verify against raw file (`terminal(command="cat ...")`) — not `custodian_issues` tool (stale cache)
- [ ] 5. Classify into four buckets: Actionable / User-gated / Legacy-inactive / Already-resolved
- [ ] 6. If any Actionable issues exist → execute fixes
- [ ] 7. If no Actionable issues → write journal with `not_activity_reason`, return `[SILENT]`
- [ ] 8. Clear `escalation_needed` flag on any resolved entries

**Escalation runner journal write — use Python always**: When running `escalation-runner` in cron context, write journals via `python3 -c "..."` with `json.dump()` and `from datetime import datetime, timezone; datetime.now(timezone.utc)`. Do NOT use `cat > file << 'EOF'` heredoc for JSON containing timestamps/run_ids. Always use `from datetime import datetime, timezone` so `datetime.now(timezone.utc)` resolves to the class method.

**Escalation runner clean verdict — actionable vs user-gated vs legacy:** When the escalation runner finds no actionable issues, classify all open entries into four buckets: (A) Actionable — execute fix; (B) User-gated — note count but do not auto-fix; (C) Legacy/inactive — ignore YAML debris in profiles with no `cron/jobs.json`; (D) Already resolved — verify config/job state and close. If Bucket A is empty, write journal with `not_activity_reason` and return `[SILENT]`. Inactive profile detection: check for `cron/jobs.json` absence (>90 days dormant). See `references/escalation-runner-clean-verdict-pattern.md`.

**Escalation runner: user-gated provider failures are not permanent kill switches:** Do NOT pause recurring cron jobs just because their last error is provider auth/credits/429/endpoint outage. First verify the provider/model live with a minimal `hermes chat -q` probe. If the provider works now, resume affected jobs and let them retry. Only pause when retry is genuinely futile until user action (e.g. revoked Google OAuth). Pausing is mitigation, never resolution. See `references/stale-provider-error-pause-loops.md`.

## Escalation Execution Loop

When an external loop invokes Custodian to *execute* fixes on escalated issues (not merely classify them):

See `references/escalation-loop-pitfalls.md` for chronic traps: journal-gap probe false positives for resolved issues, stale-error-before-reopen, cooperating with in-flight sanctioned repairs, `database is locked` verification.

1. **Verify live state BOTH directions** — (a) issue claims resolved/paused but job still `enabled`+erroring; (b) issue flags `escalation_needed: true` but job already recovered. Resolve or re-pause accordingly. (c) **sweep for missed enrollments**: any `enabled`+erroring job whose `last_error` matches a known user-gated fingerprint but is NOT in any issue's `jobs_paused`. For provider/model fingerprints, verify the provider live first. For genuinely unrecoverable domain auth, pause and add to matching issue with `paused_reason` plus re-enable check. Run `scripts/find_missed_user_gated_jobs.py`. See `references/escalation-loop-pitfalls.md` for the full detail including the false "RE-CONFIRMED LIVE" trap.
2. **Load issues from the PROFILE `issues.jsonl`** (`<hermes-home>/profiles/<profile>/commons/data/ocas-custodian/issues.jsonl`). The commons copy is a lagging sync target. Use a brace-depth parser. See `scripts/parse_issues_jsonl.py`. **DEDUPE BY LAST ROW, NOT WORST STATUS (confirmed 2026-09-28):** the file is append-only, so a change is a NEW row carrying the same `issue_id` — worst-status dedupe resurrects a resolved issue as open (measured 41 vs the true 40). Worst-status is correct only for in-place-mutating stores. **A quiet window cannot close a behavioural question:** separate "was the guard consulted?" from "did the bad outcome recur?" — if the subsystem logged only startup/registration chatter, the clean is vacuous and the honest grade is `config_verified_behaviour_unexercised`. When a component emits its own `mode=`/`status=` field, use it as ground truth instead of keyword-matching (a keyword pass scored 61.6% success for a subsystem failing every time). Full recipe: `references/escalation-runner-dedupe-and-window-evidence-pitfalls.md`. **STALE-PATH GOTCHA:** there are TWO `issues.jsonl` files — the authoritative `data/` path and a stale `journals/` copy. Always read the `data/` path. **OPEN-ISSUE FILTER:** an issue is open/actionable only if `status not in ("resolved","duplicate")` AND (`escalation_needed == true` OR `status == "user_gated"`). `parse_issues_jsonl.py`'s summary `open:` count INCLUDES `duplicate` entries. See `references/escalation-loop-issue-status-scan-trap.md`.
3. **Classify** into: Actionable (Tier 1), Code-defect fixable by this loop, User-gated (credits/API key/revoked OAuth), Already-resolved/Legacy-inactive. Verify code-defect fixes by running the ACTUAL cron script in the exact env.
4. **Execute**: Actionable → apply Tier 1 fix. User-gated provider/model outages → verify live state, keep jobs enabled and tracked. Pause only when retry is genuinely futile.
5. **Reconcile `issues.jsonl`** in one pass (safe edit pattern in `references/escalation-execution-loop.md`).
6. **Verify** then write an action journal.

**Honesty rule:** Do NOT report user-gated issues as "fixed". Pausing is mitigation, not resolution.
